## Working rhythm (please keep doing this)

Mid-session we badly over-churned the top bar + player by making many edits
across files **without committing checkpoints**, hit a "we've fucked it up"
moment, and did a full `git restore` to baseline (losing some good work with
the bad). After that we switched to a strict cadence that worked:

> **one small change → user looks on the real device → commit immediately → next.**

Also: the app's column layout is a robust flex chain
(`column: h-full flex-col overflow-hidden` · `top bar: shrink-0` ·
`main: min-h-0 flex-1 overflow-y-auto` · `play bar: shrink-0`). Because of it,
enlarging chrome **can't change screen dimensions** — the content area absorbs
it. Don't fight that with `flex-1`/fixed heights on the bars.

`tsc -p tsconfig.app.json --noEmit` was run after every change; the dev server
runs as a **systemd user service** (`systemctl --user restart allegory`,
serves `:5173`). Verify in the browser, not just types.

## Lists: how they're built (useful context)

There is **no shared list-row component** — Artists, ArtistView, Playlists,
Recently, QueueList, TrackList, Search each have their own copy of the same
flex recipe: a `flex flex-col` container of `flex items-center gap-3` rows
(`[ cover shrink-0 | name flex-1 truncate | action shrink-0 ]`). No
virtualization — every item is a real DOM node (fine at hundreds). **So a
global list change is a ~6–9 file sed, not one edit.** If we keep tuning rows,
consider extracting one shared `ListRow` so it never drifts. Search results are
the exception — a responsive CSS grid of tiles, not a flex list.
