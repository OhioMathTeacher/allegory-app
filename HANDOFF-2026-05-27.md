flattened the sidebar to 3 views, made Queue a top-level view, folded
PostPanel into NowPlaying), and the artist-editing story was built end to
end (sidecar overrides → grouping → finally proper tag rewrites + folder
renames). Plus an OOM crash diagnosis and quick fix.

## TL;DR

- App is now an **artist-centric** library. Three top-level views in the
  sidebar: **Artists / Queue / Playlists**. The whole Albums grid (5 view
  modes, ~1000 LOC in `Library.tsx`) is gone.
- **Queue is a real view** (recently played → current → up next, one
  scrollable list). Save-as-playlist + clear-up-next moved into its
  header.
- **Artist editor** (long-press an artist card, or the "Edit" button in
  ArtistView) does a **real** rename: ffmpeg rewrites the `artist` /
  `album_artist` tags on every track, and the artist's folder gets
  renamed on disk. When the target folder already exists it **merges**
  the source's album subfolders in.
- **Album editor** already existed (long-press an album card); also added
  an explicit **Edit** button to AlbumView for parity.
- **OOM crash** on desktop Chromium diagnosed: it was `partition_alloc`
  raising SIGILL on out-of-memory, caused by ~1.5 GB worth of decoded
  cover art. Quick fix: dropped grid cover request from 420→256 px and
  added `decoding="async"` to `<Cover>`. **Real fix is virtualization,
  still pending.**
- **Mobile niceties** added earlier in the day: top-bar layout, drawer,
  Apple Music–style scroll-driven letter index, scrub zone, big mobile
  player controls, PWA standalone meta. (Already shipped earlier; not
  the focus of today's handoff.)
- **Phone-as-remote** shipped earlier today (WebSocket relay, host
  candidate list, Cast button). Already in `origin/main`. Not touched
  today beyond reading.

## How the artist rename actually works now

User flow:

1. **Long-press** an artist card (Grid, Small grid, or List view) **or**
   click the **Edit** button on the ArtistView page.
2. Modal opens. Type a new name. Click Save.
3. Modal sits for a few seconds while the server works (no progress bar yet).
4. Toast: "Rewrote N tracks." (or "Merged N tracks into existing folder."
   if the target name already existed).
5. Modal closes; React Query invalidates; list refreshes.

Server-side flow (`renameArtist` in `server/metadata.ts`):

1. Look up the `ScannedArtist` by id; grab its `dir` + `albumIds`.
2. Walk all tracks (`artist.albumIds → album.trackIds → track.path`) and
   snapshot the file paths **before** any filesystem moves.
3. For each track, run
   `ffmpeg -i in -map 0 -c copy -metadata artist=X -metadata album_artist=X out`
   and atomic-move the temp over the original. (Same `writeTrackTags`
   helper the album editor uses.)
4. Compute the new folder path (`<musicDir>/<newName>`).
   - **If it doesn't exist**: `fs.rename(oldDir, newDir)` (with a cross-fs
     fallback that does mkdir + per-child move + rmdir).
   - **If it does exist**: this is a **merge**. Walk the children of
     `oldDir`, verify no name collision with anything already in
     `newDir`, then move each child in. `rmdir` the now-empty source.
5. Return `{ tracksRewritten, folderRenamed, mergedInto? }`.
6. Caller (`router.ts`) fires `void library.scan()` (no await — client
   refresh happens via React Query invalidate).

This is why **renames are now permanent** and propagate to other players:
the file tags really change, and the scanner derives artist names from
folder structure, so the folder move is what the listing actually
follows.

## Known issues / rough edges

### Renames take time, with no progress bar

The rename runs ffmpeg synchronously per track. For an artist with
50 tracks, the modal sits there for ~30–60 seconds with just a spinner.

- **Not yet:** progress reporting (e.g. "Rewriting 12 / 47 tracks…").
- **Won't lose work:** if the user closes the tab, ffmpeg keeps running
  server-side. They just won't see the result until they reload.

### The merge case can throw "already exists"

`renameArtist` errors out with "Can't merge — \"X\" already exists under
\"Y\". Resolve manually and try again." if any album folder being moved
in collides with one already in the destination. This is a safety check,
not a bug — but it means if you somehow have **two** "Houdini" folders
across two source artists when you merge into one Melvins, you'll have
to rename one of them first.

### Pre-existing lint errors (not from today)

- `src/components/AppShell.tsx:86` — `setState` in effect (firstRun
  auto-open). Pre-existing.
- `src/lib/player.tsx:79` — `audioRef.current` accessed during render
  (lazy-init pattern). Pre-existing.
- `server/metadata.ts:32` — `no-control-regex` in `safeFsName`. The
  control-character strip is intentional. Pre-existing.

### Memory / OOM

Quick fix in place (smaller cover requests + `decoding="async"`). **The
real fix is virtualizing the long lists** (Artists view especially, with
518 entries × 256-px circles). Use `@tanstack/react-virtual`. ~1–2 hours
of work; deferred. If you see another `Aw, Snap! SIGILL` crash, this is
why — reload as a stopgap.

### React Query cache after rename

After a rename, we `invalidateQueries()` (all of them). This forces
refetches of the artist list and any open album/track lists.
**ArtistView's H1 still uses the `artist` prop**, which is captured at
navigation time. If you rename an artist while inside its page, the H1
won't update until you navigate away and back. Low priority — most
people rename from the list, not from inside the page — but worth
knowing.

### 1. AcoustID + MusicBrainz "lookup metadata"

The user explicitly asked: "could we have a button that takes a short
sample of the song, identifies its thumbprint, and updates metadata from
the popular free DB?" Yes — it's AcoustID (Chromaprint fingerprinting) +
MusicBrainz (the actual metadata).

**Stack:**

- Install `fpcalc` system binary (`dnf install chromaprint-tools` on
  Fedora). Server runs it on one of the artist's tracks.
- AcoustID API: free, needs a registered API key. Rate limit ~3
  lookups/sec. Returns `{ id, score, recordings: [{ id, title,
  artists }] }`.
- MusicBrainz API: free, no key required, ~1 req/sec rate limit.
- Cover Art Archive for cover images (free).

**UX (per the conversation):** today's long-press → editor flow becomes
long-press → **small menu**:

- Edit name & cover (current behavior)
- Look up metadata (new)
- (room for more — Merge with…?)

When "Look up" is picked, take a fingerprint of one representative
track, query AcoustID, present the top 1–3 candidates ("Did you mean:
Melvins — *Houdini* (1993)?"), let user confirm; on confirm, fall
through to the same renameArtist flow with the suggested name.

Scope estimate: a focused half day.

### 2. Issues queue (flag from phone, fix from desktop)

**Design:**

- Persistent file: `.allegory-cache/issues.json`. Schema like

- A small "flag" icon on artist (and maybe album) cards. Tap from

Pairs naturally with AcoustID lookup — flagged-on-phone items become a
queue that desktop can run AcoustID against in bulk.
